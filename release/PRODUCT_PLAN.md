# MORROW 제품 고도화 기획

이 문서는 MORROW를 “프로필을 많이 넘기는 서비스”가 아니라 **안전하게 대화를 시작하고 실제 약속까지 이어지는 서비스**로 운영하기 위한 제품 기준이다. 숫자는 아직 실제 회원 데이터로 검증되지 않은 목표치이며, 운영 대시보드가 쌓인 뒤 코호트별로 조정한다.

## 1. 제품 북극성

**North Star:** 신규 회원이 가입 후 7일 안에 안전한 첫 대화를 시작하고, 서로 가능한 시간과 공개 장소를 합의하는 비율.

핵심 퍼널은 아래처럼 짧고 명확하게 유지한다.

```text
랜딩 → 소셜 로그인 → 필수 동의·성인 확인 → 프로필 완성
  → 설명 가능한 추천 → 관심 보내기/받은 관심 응답 → 상호 매치
  → MORROW Sync 또는 첫 메시지 → 공개 장소·시간 제안
  → 안전 확인 → 만남 후 피드백
```

## 2. 다시 정의한 사용자 약속

- **시간이 맞는 사람부터:** 공통 가능한 시간을 추천 이유의 앞쪽에 보여준다.
- **먼저 온 관심을 놓치지 않게:** 나에게 먼저 관심을 보낸 실제 회원을 매치 화면에서 확인하고 한 번에 응답한다.
- **연락처는 마지막까지 비공개:** 첫 대화·장소·시간은 앱 안에서 처리한다.
- **사진보다 신뢰를 우선:** 사진 검수, 계정 상태, 차단·신고, 약속 전 안전 확인을 같은 흐름에 둔다.
- **실제 데이터만 사용:** 가상 회원·후기·매치·성공률을 제품 화면에 넣지 않는다.

## 3. 분기별 고도화 순서

### Q0 — Reliability & Trust (운영 기반, 완료/유지)

목표는 40,000명 규모의 공개 유입을 받아도 핵심 요청이 조용히 실패하지 않는 것이다.

- Flyway 마이그레이션이 JPA 트래픽보다 먼저 실행되도록 기동 순서를 고정한다.
- `/api/health`가 DB와 필수 테이블을 함께 확인하는 readiness 계약을 제공한다.
- Redis 분산 요청 제한, WebSocket 사용자별 메시지 예산, Origin 검사를 유지한다.
- 사진·채팅 첨부는 매직 바이트, 크기, 소유권, 검수 상태를 서버에서 재검증한다.
- 운영 전 실제 두 계정으로 OAuth → 매치 → 채팅 → 약속 → 신고 왕복을 통과시킨다.

출시 게이트: 빌드·컨텍스트 테스트 통과, readiness 200, 5xx·마이그레이션 오류 0, 모바일 360px과 데스크톱 1440px에서 핵심 CTA가 보일 것.

### Q1 — Activation Loop (이번 릴리스)

가입 직후 “누가 나에게 관심이 있는지”를 알 수 없다는 초기 이탈을 줄인다.

- `받은 관심`을 매치 화면 상단에 실제 데이터로 노출한다.
- 관심을 보낸 사람의 사진·공통 취향·가능 시간·추천 이유를 한 카드에서 보여준다.
- `관심 보내기`를 누르면 기존 매치 트랜잭션을 사용해 즉시 상호 매치로 연결한다.
- 패스 후에는 받은 관심 목록에서 제거하고, 차단·비활성·기존 매치 계정은 서버 쿼리 단계에서 제외한다.
- 같은 프로필을 다시 응답하지 않도록 수신 목록 쿼리에서 내가 이미 보낸 반응을 제외한다.

측정 이벤트(서버 로그에는 개인 식별값 대신 내부 사용자 ID 해시 사용): `received_interest_viewed`, `received_interest_like`, `received_interest_pass`, `match_created`.

### Q2 — Conversation Quality

목표는 매치 이후의 정적 화면을 “다음 한 문장”이 있는 대화로 바꾸는 것이다.

- 공통 관심사와 가능한 시간을 바탕으로 첫 메시지 제안을 만든다. 자동 발송은 하지 않고 사용자가 수정·전송한다.
- 24시간 동안 답장이 없을 때만 한 번의 부드러운 리마인드를 제공하며, 알림 설정을 존중한다.
- 채팅 화면에 `Sync → 사진 → 약속`의 진행 상태를 보여주되 대화를 재촉하지 않는다.
- WebSocket이 끊겨도 DB 이력과 전송 중·실패·재시도 상태가 일관되게 보이도록 한다.

출시 게이트: 멱등 `client_id`, 읽음 처리, 첨부 권한 검증, rate limit, 재연결 시 중복 메시지 없음.

### Q3 — Date Execution & Safety

목표는 “언젠가 만나자”에서 실제 약속으로 넘어가는 마찰을 낮추면서 안전을 강화하는 것이다.

- 두 사람의 공통 시간을 기반으로 제안 가능한 슬롯을 먼저 보여준다.
- 카카오 장소 결과는 공개 장소·상호명·도로명·지도 링크를 함께 기록한다.
- 약속 4시간 전부터 양쪽의 안전 확인을 받고, 미확인 시 조용한 리마인드를 보낸다.
- 불참·불안전 피드백은 신뢰 점수와 운영 큐에 반영하되, 자동 제재 대신 검토 가능한 신호로 취급한다.
- 대화 종료·차단·신고는 약속 화면에서도 두 번 이상 찾지 않도록 한다.

출시 게이트: 약속 상태 전이(대기→수락/거절) 검증, 과거 시간 차단, 차단 즉시 매치·사진 접근 중단, 신고 SLA 대시보드.

### Q4 — Growth & Sustainable Business

목표는 무료 핵심 경험을 훼손하지 않는 방식으로 유입과 운영을 확장하는 것이다.

- 추천 코드와 공유 랜딩은 실제 초대한 회원과 가입 전환만 집계한다.
- 대학·지역 커뮤니티 유입은 전용 캠페인 파라미터로 코호트를 구분하되, 개인정보를 URL에 넣지 않는다.
- 7일·30일 유지율, 첫 대화 응답률, 약속 제안률, 신고율, 처리 시간을 코호트별로 본다.
- 결제는 추천·채팅·안전 기능을 잠그지 않는 선택형 가치(큐레이션 지원, 고급 필터 등)부터 소규모로 검증한다.
- 가격과 결제 API는 실제 비용·환불·전자상거래 약관·세금 처리가 준비된 뒤 별도 기능 플래그로 출시한다.

## 4. UX 기준

- 한 화면의 주 행동은 하나만 둔다. 추천에서는 `관심 보내기`, 매치에서는 `대화 이어가기`, 약속에서는 `시간 제안`이 우선이다.
- 카드에는 이름·나이보다 `왜 추천됐는지`와 `언제 만날 수 있는지`가 먼저 읽혀야 한다.
- 모바일 360px에서 가로 스크롤 없이 사용하고, 모든 주요 버튼은 최소 44px 터치 영역을 갖는다.
- 긴 한국어 문장은 단어 단위로 자연스럽게 줄바꿈하고, 사진이 없는 실데이터도 빈 화면처럼 보이지 않게 설명한다.
- 로딩·빈 상태·오류·성공 상태를 각각 제공하고, 네트워크 재시도는 사용자의 입력을 잃지 않게 한다.

## 5. 데이터·운영 원칙

- 프로덕션에는 시드 회원이나 가짜 성공 후기 데이터를 넣지 않는다.
- 위치는 선택한 활동 지역의 근사 중심만 저장하고 정확한 집 주소를 수집하지 않는다.
- 탈퇴·차단·신고·사진 검수 상태는 API와 WebSocket 양쪽에서 재검증한다.
- 모든 목록 API에는 상한과 정렬 기준을 두고, 수신 관심·추천·메시지의 hot path에는 전용 인덱스를 둔다.
- 운영자는 신고·사진·본인 확인을 감사 로그와 함께 처리하고, 처리 결과를 사용자에게 명확히 알린다.
